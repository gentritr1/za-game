Two pizzas at once

Fade a transparent picture in over another transparent picture and the player sees both — which is not what a two-frame loop is supposed to look like.

Each side panel of the ZA! cabinet has an art window with a mural in it: a chef tossing dough. It runs as a two-frame loop, the way an arcade attract screen does. Frame A, frame B, back to A, forever.

The murals started out opaque, and the loop was one animation on one element: frame B’s opacity goes on, then off. Frame A sits underneath and is simply always lit — when B is up it covers A, and when B is down you see A again. Correct, cheap, shipped.

Then the murals were redrawn as transparent vinyl, so the cabinet’s checkerboard could read through them. Same code. Same timings. And now half of every cycle showed two discs of dough at once, each visible through the other.

Only one frame was animated

That was the whole bug, and it was invisible while the art was opaque. “B covers A” is not something CSS enforces; it is something opacity was doing for us, as a side effect of the pixels. The instant B gained transparency, A kept being fully lit underneath and showed through every transparent pixel of B.

It gets worse if the frame fades rather than flips: halfway through you have one frame at 100% and another at 50%, stacked. That is a double exposure. But even a hard flip is wrong here, because the frame underneath was never told to leave.

The model you actually want is blunt: exactly one frame on screen at any instant. Which means both frames must be animated, on the same clock, with mirrored keyframes — A hides at precisely the moment B shows. That is counter-phasing.

A rides along, always lit

.frame-a { opacity: 1; }
.frame-b { animation: flip-b 1800ms
           steps(1, end) infinite; }

Mirrored keyframes

@keyframes flip-a {
  0% {opacity:1} 50%,100% {opacity:0} }
@keyframes flip-b {
  0% {opacity:0} 50%,100% {opacity:1} }

The easing is doing real work

steps(1, end) is what makes this a flipbook rather than a fade. Under a step easing each interval holds its own start value and then jumps at the end of it: opacity is 1 or it is 0, and never 0.4 on the way. A bulb is lit or it is not.

That also removes a whole class of near-miss. With a smooth easing the two frames are only correct if the browser evaluates both at exactly the same moment; with steps(1, end) there is no in-between value for them to disagree about.

Ours run on a 1800 ms cycle — 900 ms a frame — and the right-hand panel starts 450 ms late, so the two windows do not tick in unison and the cabinet does not pulse at you.

The generalisation is worth more than the fix: an opacity change is only a swap when what is on top is opaque. The instant a layer gains transparency, every “it covers the one below” assumption in your animation quietly stops being true, and nothing errors.

HOUSE RULE

Transparent frames in a two-frame loop must counter-phase — and steps(1, end) is the easing that keeps a flipbook a flipbook.

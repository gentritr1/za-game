No. 01 · Instruments

The frozen arcade

A browser tab you cannot see stops running your animations — and every tool you point at it will still hand you a number.

We put a probe on the deal cascade, the animation that flicks seven cards out to your hand, and asked it how evenly the frames were arriving. It answered: a 95th percentile of 1969 milliseconds.

That is a catastrophic number. It also has the shape of a real one — a percentile, over a real window, taken from a real page. We were most of the way to optimising the deal before anyone questioned it.

What was actually happening

The page was running in a browser pane that was hidden. Browsers treat a hidden tab as a tab nobody is watching: CSS animations pause, and requestAnimationFrame — the callback that fires once per drawn frame — stops firing almost entirely. That is a battery feature working correctly.

So the probe did not sample a slow deal. It sampled almost nothing. Over that window, at that frame rate, it should have collected 223 frames. It collected 5. The 1969 ms was simply the gap between two of those five samples, minutes apart.

That is not a measurement with a bad result. It is a broken instrument that outputs a number, which is far more dangerous, because a number invites you to act on it.

The same freeze produced a second ghost the same week: dialogs screenshotted blank. Frame, border, nothing inside. Their contents were sitting at the entry animation’s opacity: 0, and the animation meant to bring them up never advanced a step.

Reconcile the count before you quote the percentile

Do one division first: how long was the window, multiplied by how many samples per second you expected. If that says 223 and your array holds 5, stop — nothing computed from that array means anything, however plausible it looks.

Then print the reconciliation next to the number, so the next reader can check it without re-deriving it. A percentile over an unverified sample count is not a measurement.

Do not photograph motion — ask it

A screenshot of something moving tells you what one instant looked like, and in a frozen tab that instant is the first one, forever. Ask the browser for the state instead:

  • getComputedStyle(el) — what is actually on screen right now.
  • el.getAnimations() — what is running, and how far through it is.
  • anim.finish() or setting anim.currentTime — move the animation where you want it, then look.

Proves nothing

await screenshot();
expect(ring).toBeVisible();

Proves it

ring.getAnimations()
    .forEach((a) => a.finish());
expect(getComputedStyle(ring)
  .opacity).toBe('1');

There is one more edge here, and we hit it from both sides. A transition sampled at currentTime 0 reads its start value. A focus ring that fades in perfectly and a focus ring that never lights are identical at time zero. Somebody nearly “fixed” correct code on that evidence; finishing the animation through the Web Animations API showed the end state had been right the whole time.

The general shape: verify in the environment that produced the bug, not in a friendlier one. If the thing you are testing only misbehaves in a hidden pane, a visible pane is not a test.

HOUSE RULE

Reconcile sample count against window × expected rate before quoting any percentile — and never verify motion with a picture of motion.

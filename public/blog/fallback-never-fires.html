The fallback that never fires

A var() fallback rescues a custom property that was never set. It does nothing for one that is set to something unusable — and CSS will not tell you which case you are in.

ZA! draws a cabinet around the playfield: a panel down each side, like the sides of an arcade machine. How wide those panels are is one line of arithmetic — whatever is left over once the playfield has taken its share, split in two.

The playfield’s share is a knob called --play-max, and at the time it was uncapped. We wrote “uncapped” the way it reads in English: none.

Panels came out `auto`

--play-max: none;
--panel-w: max(0, (100vw - var(--play-max)) / 2);

The panels computed to width: auto instead of zero, and a popover underneath measured itself against the wrong number. We assumed the var() fallback had us covered. Covering exactly this is what fallbacks are for.

Two traps in one line

First: none is not a length. calc() and max() do arithmetic on lengths, and 100vw - none is not arithmetic. The declaration becomes invalid — but not while the file is being parsed. It happens at computed-value time, once the variable has been substituted in, which is far too late for anything to warn you. The property falls back to its initial value, which for width is auto, and the page renders happily.

Second, and this is the real lesson: a var() fallback only fires when the property is missing. Writing var(--play-max, 100vw) means “if nobody has set --play-max, use 100vw”. Somebody had set it. It was none. As far as var() is concerned nothing is wrong: there is a value and it is substituting it, exactly as asked. The breakage happens one step later, in arithmetic that var() knows nothing about.

Custom properties are almost untyped — a variable holds a run of text, and whether that text makes sense is only discovered where it lands. The fallback guards the wrong question.

(A third, smaller lie in the same line: max(0, …) next to a length needs 0px. A bare 0 is a number, not a length.)

The fix: a length-valued twin

Keep the knob as the statement of intent, and give the arithmetic its own variable that is guaranteed to be a real length. The arithmetic never reads the knob directly.

The twin

--play-max: 1900px;                       /* intent */
--play-cap: min(100vw, var(--play-max));  /* always a length */
--panel-w:  max(0px, (100vw - var(--play-cap)) / 2);

While the playfield is uncapped, --play-cap simply is 100vw, so the leftover is zero and the panels disappear the way they should. Nothing downstream ever touches a value that might not be a length.

The other half of the pattern is a sentence, written in a comment right beside the code: panel-w × 2 + play-cap == 100vw, on both sides of the cap. That is an invariant — a thing that must stay true. It costs one line, it is checkable by hand, and it is what tells the next person whether the change they are about to make is allowed.

HOUSE RULE

A present-but-unusable custom property never falls back. Gate arithmetic behind a length-valued twin, and write the invariant down next to it.
